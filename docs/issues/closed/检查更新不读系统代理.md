# 检查更新不读系统代理

状态：已完成（Windows 和 macOS 开着系统代理的真机实测由负责人做，见「没验证的」）

## 要解决什么

检查更新的请求只认环境变量里的代理设置，不读 macOS 和 Windows 的系统代理。靠系统代理才能打开 GitHub 的用户，浏览器能打开发布页，软件却连不上。

对这部分用户的后果：

- 启动时的自动检查失败，齿轮上不出现红点。
- 手动点「检查更新」，看到「检查更新失败，请稍后再试」。
- 其它功能不受影响，用户可以自己去发布页下载新版。

## 已定的决定

| 事项 | 决定 |
| --- | --- |
| 谁去读系统代理 | Rust 侧读（做法 A），不改由工具栏网页去查 |
| Windows 怎么读 | 包装层自己读注册表里的系统代理（`winreg`，就是 `ureq` 的 `win-system-proxy` 用的那个库），只用 HTTPS 那一项。原定打开 `win-system-proxy`，审查查出它会把系统设置里的排除项套到环境变量代理上（系统代理关着也会），还读不懂按协议分开（`http=…;https=…`）和带协议（`https://…`）的写法，所以不开它 |
| macOS 怎么读 | 跑系统自带的 `scutil --proxy`，读「安全网页代理（HTTPS）」那一项；不加新的 Rust 依赖 |
| 先后 | 环境变量里的代理优先；没有才用系统设置里的；都没有就直连 |
| 排除项 | 环境变量 `NO_PROXY` 对两种来源的代理都生效；系统设置里的排除项只配系统设置里的代理，按系统的通配写法匹配（`*` 可在开头、中间、结尾，如 `*github*`） |
| 什么样的系统代理算数 | http 或 https 代理，有主机、有非零端口；Windows 省略端口时用协议默认端口（http 80、https 443），和系统一样；地址里带的账号密码保留；其余情况当作没有，直连 |
| 读不出来时 | 当作没有系统代理，照常直连，检查不因此报错 |

## 做法

- `src-tauri/src/update.rs` 的 `update_proxy` 决定走哪个代理，启动检查和手动「检查更新」都经过它；`fetch_latest` 只用传进来的代理，不再让 `ureq` 自己去读环境变量。
- 环境变量里的代理用 `ureq` 的 `Proxy::try_from_env`（不开 `win-system-proxy` 时它只读环境变量）。`update.rs` 里有守卫测试盯着 `Cargo.toml`，不许给 `ureq` 开 `win-system-proxy`。
- 系统设置里的代理：两个平台各自读出「HTTPS 代理地址 + 排除项」，再由同一个 `build_system_proxy` 校验并建代理，同时加上环境变量 `NO_PROXY`。
  - macOS：`/usr/sbin/scutil --proxy` 输出最外层的 `HTTPSEnable` / `HTTPSProxy` / `HTTPSPort` 和 `ExceptionsList`。只开了 HTTP 代理时不用：检查更新只发 HTTPS 请求，系统对 HTTPS 请求也只用 HTTPS 那一项。
  - Windows：注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyEnable` / `ProxyServer` / `ProxyOverride`。`ProxyServer` 按协议分开时只用 `https=` 那一项，没有就直连；带 `https://` 时用 TLS 连代理。系统代理关着时排除项也不读。
- Linux 只认环境变量。
- 测试：排除项通配匹配（`*github*`、`*.local`、`127.*` 等）；两个平台的系统设置各种写法（开、关、只开 HTTP、按协议分开、带协议、缺地址、端口缺失/写错/为 0、只有网卡自己的设置、读不懂）；环境变量优先且有环境变量时不读系统设置；请求真的经由本机假代理发出：按协议分开时只到 `https=` 那个端口，Windows 通配排除项命中时代理收不到请求，命中 `NO_PROXY` 时代理收不到请求、没命中照常走代理。

## 已验证的（2026-11-28，macOS，开发机）

- 没开任何代理：照常直连 GitHub，查到最新版 0.1.4。
- 设 `HTTPS_PROXY` 指向本机临时代理：请求经代理（代理收到 `CONNECT github.com:443`），查到 0.1.4。
- 用 `scutil --proxy` 格式的「开着 HTTPS 代理」输出、用 Windows 按协议分开的写法，各构造出指向本机临时代理的系统代理：请求都经代理查到 0.1.4。没有改这台机器的系统设置。
- 读注册表那段代码在 Mac 上按 Windows 目标单独编译并过了静态检查；完整的 Windows 编译和测试由 GitHub 上的检查跑。

## 没验证的（要负责人本人做）

- Windows：在系统设置里开代理（例如 Clash、v2rayN 的「系统代理」），直连 GitHub 不通时，启动检查和手动检查都能查到新版。
- macOS：在系统设置里开 HTTPS 代理，直连 GitHub 不通时，从访达打开的应用里手动检查能查到新版。

## Agent Brief

**Category:** bug

**Summary:** 检查更新的请求要走 Windows 和 macOS 系统设置里的代理。

**Current behavior:**
检查更新（启动时一次、设置页面里手动一次）只认环境变量里的代理。用户只在系统设置里配了代理（例如 Clash、V2rayN 设的系统代理）、直连 GitHub 不通时，两种检查都失败。

**Desired behavior:**
- Windows：检查更新走系统设置里的代理，由包装层自己读注册表。
- macOS：检查更新由 Rust 读系统设置里的 HTTPS 代理并使用它。
- 环境变量和系统代理同时存在时，环境变量优先。
- 没设任何代理时，行为和现在一样：直连。
- 读系统代理失败时，当作没有系统代理，不让检查因此报错。

**Key interfaces:**
- 构造 `ureq::Agent` 的地方：代理配置从「只读环境变量」改成「环境变量优先，其次系统代理」。
- `src-tauri/Cargo.toml`：Windows 上加 `winreg` 读注册表（不开 `ureq` 的 `win-system-proxy`）；macOS 用系统自带的 `scutil --proxy`，不加依赖。

**Acceptance criteria:**
- [ ] 开着系统代理、直连 GitHub 不通时，启动检查和手动检查都能查到新版。
- [x] 没设代理时，检查更新照常工作。
- [x] 环境变量和系统代理同时存在时，用环境变量里的代理。
- [x] `pnpm check` 通过。
- [ ] Windows 在虚拟机里实测通过（负责人做）。
- [ ] macOS 实测通过（负责人做：要临时打开系统代理）。

**Out of scope:**
- PAC（自动代理配置脚本）和 SOCKS 代理。
- 「下载新版」按钮：它让系统浏览器打开发布页，本来就走系统代理。
- 粉笔网站的请求：由 WebView 自己处理。
