## 1. 建议先做什么

建议第一轮围绕“让 AI 每次修改都有明确边界、有可重复的验证、有可审阅的小改动”完善项目。优先整理真实行为、建立登录与导航回归测试、补充日常 CI，再修复复现出来的问题。

产品继续保持轻量：打开粉笔题库、保留网站登录与做题流程、适度裁剪页面。暂不引入前端框架、账号体系、题目采集、云同步、自动更新或大型设置中心。

这里将 vibe coding 最佳实践落实为：先定义用户可见的验收结果，再让 AI 小步实现并交付证据；用简短的项目约束和可靠检查减少反复人工纠错。探索、规划、实现分阶段，以及为 AI 提供可执行验证，参考 [Claude Code 官方最佳实践](https://code.claude.com/docs/en/best-practices)。以下具体优先级与设计为结合本仓库作出的建议。

## 2. 现状与判断依据

本轮依据静态阅读，不将潜在时序问题写成已在真实粉笔网站复现的故障，也不把仓库历史“实测”描述当作当前跨平台验证结果。

| 观察 | 仓库依据 | 影响与建议 |
| --- | --- | --- |
| 架构小且职责集中 | `src-tauri/src/lib.rs` 创建远程 WebView，`init.js` 负责页面辅助 | 保留 Tauri + 原生 JS，按可测试边界作有限拆分 |
| 已有锁文件、快速开发入口、三平台 Release 草稿流水线 | `pnpm-lock.yaml`、`Cargo.lock`、`scripts/dev-run.sh`、`.github/workflows/release.yml` | 延续现有基础，无需重建工具链 |
| 说明与实现有冲突 | `CONTRIBUTING.md` 写“不模拟点击”；`init.js` 的 `doOpenLogin()` 调用 `btn.click()`；Rust 文件头说不读 cookie，但有 `credentials_present()` | AI 容易依据过期约束做错修改，优先统一描述 |
| 登录提示有多个时间来源 | JS 启动提示延迟 800ms；Rust settle 等待 1500ms，且计时起点不同 | 缓存为 false、会话稍后恢复时存在误弹风险，需要可控时钟测试 |
| 登录按钮重试不能完整取消 | `openLoginOnce()` 的 interval 不检查 `verifiedLoggedIn`；成功通知只设置标记 | 验证成功后按钮才出现的场景，重试可能继续点击 |
| 练习保护没有覆盖每个弹窗入口 | `goToCatalog()` 有保护，但启动未登录分支及 `__fenbiLoggedOut` 最终调用的 `openLoginOnce()` 没有统一保护 | 从练习页启动或检查与执行之间切换路由时，需要验证是否误弹 |
| 练习区失效后缺少明确的延迟处理流程 | Rust 检测失效后已把内存状态改为 false；正式 JS 没有对应的 SPA 离开练习区处理 | “做题时不打断，结束后提示”尚需验证；不应仅依赖下一次状态变化 |
| cookie 存在被当成登录依据，读取失败映射为 false | `credentials_present()` 只按名字检测，并 `unwrap_or(false)` | 区分“凭证存在”“服务端认可”“读取失败”；读取失败不能直接当成登出 |
| 新页面检查可能被心跳休眠延迟 | watcher 首次判定后可睡眠五分钟，页面代号变化不会主动唤醒 | 用测试验证新加载期间响应延迟，再决定是否改为可唤醒等待 |
| 发布权限与开发用途混在一起 | capability 包含 `https://*.fenbi.com`、本地测试地址和 `core:default`；权限声明包含 debug 命令 | 核对实际权限与来源，按构建模式隔离；debug 命令目前有条件编译，不等于已在 release 暴露 |
| 没有发现已提交的自动测试或 PR 检查工作流 | `package.json` 无检查脚本；`.github/workflows` 只有 tag 发布 | 普通代码改动缺少自动反馈 |
| 离线页面尚未形成恢复闭环 | 根目录 `index.html` 是占位页；`pnpm build` 只建 `dist`；窗口直接加载远程地址 | 未见将页面复制进产物及加载失败切换逻辑，不能宣称离线兜底已可用 |
| 开发启动脚本偏 Unix | `pnpm dev` 调用 Bash、`pkill`，可执行文件路径无 `.exe` | 三平台打包支持应与三平台开发、运行验证分开说明 |

## 3. 第一阶段：把项目变成可验证的 AI 协作工程

### 3.1 精简项目约束与说明（P0）

拟新增简短的根目录 `AGENTS.md`，只写任务边界、有效命令入口、必须保护的用户流程、验证要求，以及详细文档链接。不要复制整份实现说明或堆叠通用编码准则。

拟同步修订 `CONTRIBUTING.md`、README 和相关代码注释：

- 明确当前确实有 cookie 观察、登录按钮点击、目录重定向和手动刷新；分别说明触发条件。
- 把“登录记录”“本地凭证信号”“网站真实会话”分清；删除“本地检测就是服务端权威”的保证。
- 将跨平台构建与真机验证分列，历史站点观察注明平台、日期与复核方法。
- README 的“长期有效”“不会影响账号安全”等绝对承诺改为准确表述：会话受网站控制；Rust 会读取 cookie 用于本地判断，不能称应用完全不接触凭证。
- 区分开发构建、脚本同步与发布构建；明确 `pnpm build` 当前不验证应用。

验收：文档与代码的登录时序、支持范围、调试开关一致；新任务能快速找到运行和验证入口；本阶段不改变用户行为。

### 3.2 先建立可重复的行为测试（P0）

优先利用 Rust 原生测试和 Node 内置测试能力；只有需要真实 DOM、计时器与导航联动时才增加浏览器测试依赖。本地模拟站点采用合成页面和假凭证，不接入真实账号。

拟新增：

- `tests/fixtures/`：目录、登录弹窗、练习、报告、延迟恢复等最小模拟页面。
- Rust 测试：凭证读取失败、缓存读写异常、事件顺序、路由保护及可唤醒调度。
- JS 行为测试：按钮延迟出现、重复通知、取消重试、目录防循环、练习区保护、SPA 路由变化。
- `pnpm check`：明确组合 JS 语法检查、Rust 格式与静态检查、核心测试；退出码如实反映失败。

测试使用可控时间和事件序列，避免真实等待五分钟。不得写一个复制生产算法的“正确实现”来互相验证；断言应观察弹窗次数、导航次数、缓存变化和定时任务是否取消。

验收：登录时序修复前，相关用例能稳定暴露问题；修复后通过。模拟页通过只能证明包装层行为，不能代替实际 WebView 登录验证。

### 3.3 增加日常 CI（P0）

拟新增 `.github/workflows/check.yml`，用于 PR 和普通分支推送；继续保留 tag 触发的 Release 草稿流程。

- 日常检查运行上述检查入口，安装 Tauri 所需系统依赖，使用锁文件。
- PR 工作流采用只读权限，不需要发布凭证。
- 关键原生改动补充三平台编译检查；分清编译检查与 UI 冒烟测试。
- tag 发布前验证 tag 与 `package.json`、`Cargo.toml`、`tauri.conf.json` 的版本一致，锁文件元数据同步。
- 明确 Node、pnpm、Rust 工具链版本策略；避免借补 CI 顺便进行大范围依赖升级。

验收：故意引入语法错误或核心测试失败时，PR 检查失败；检查通过也不会自动创建公开 Release。

## 4. 第二阶段：针对登录、导航与权限做小步修复

### 4.1 统一登录辅助决策（P0）

目标：已恢复登录时不误弹、练习过程中不自动弹窗或跳转、离开练习后能处理待提示事项。

建议先建立状态转换表，再按测试需要从 `lib.rs` 提取登录决策与调度逻辑，保留 WebView 和文件访问适配层。无需一次拆成许多文件。

拟采用以下语义：

| 输入或情境 | 拟定行为 |
| --- | --- |
| 历史记录存在，但站点尚未恢复 | 记录仅作启动提示依据，不把它当服务端确认 |
| cookie 读取异常 | 保持未知，不覆盖历史状态、不主动弹框 |
| 观察到凭证 | 取消包装层尚未执行的登录提示；不保证服务器仍接受凭证 |
| 确需提示且当前在练习区 | 记为待提示，执行点再次检查路由 |
| SPA 导航离开练习区 | 重新评估待提示，满足条件时只提示一次 |
| 登录或按钮重试进行中收到重复事件 | 合并事件，取消旧定时任务，避免重复点击 |
| 窗口关闭或新页面加载 | 取消旧任务；新页面检查不受五分钟休眠阻塞 |

需特别验证 `/spa/tiku/...` 与 `/tiku/...` 路径形式、不同域名跳转，以及 `sessionStorage` 受 origin 隔离对“登录后回目录”标记的影响。路由规则应共享来源或以同一组样例约束 Rust 与 JS。

不通过新的私有接口探测、读取题目数据或强制刷新来解决登录问题。若网站没有可靠的会话信号，优先保持未知并让网站自身登录流程处理，避免用更多定时器制造确定性假象。

验收以第 6 节矩阵为准。暂不预设“将 800ms 改成更大数值”就是解决方案。

### 4.2 收紧远程调用与调试边界（P1）

Tauri capability 决定哪些窗口和来源可以调用原生命令，多个 capability 的权限会合并。因此需要核对最终有效权限，而非只检查某一个文件。[Tauri 官方 capabilities 文档](https://v2.tauri.app/security/capabilities/)

拟修改范围：`capabilities/`、`permissions/`、`lib.rs` 及调试脚本。

- 根据实际登录、目录、练习跳转链确认必要域名，再缩小 `*.fenbi.com` 的授权面，避免直接猜测白名单造成登录回归。
- 开发用 localhost 授权、测试 URL 覆盖、心跳覆盖与 debug 命令权限按构建模式隔离。
- 核对自定义 command 的注册和权限约束是否实际生效；增加非授权来源调用失败的验证。
- 用序列化生成 JS 字符串，并校验入口 URL；替换当前仅处理反斜杠和双引号的转义函数。
- 诊断信息只保留事件、时间和必要路径；清理完整 URL query 等可能携带用户信息的字段。
- 检查 `csp: null` 与远程文档的实际关系，不能假设随意加一份 CSP 就能控制远程网站全部资源。

验收：允许来源仍能完成目录与练习流程；非授权来源无法调用包装层命令；release 不授权本地测试页面，调试入口不可用；日志不包含凭证值或完整敏感 URL。

## 5. 第三阶段：补齐用户体验与交付（P1 / 可选）

### 5.1 离线与加载失败恢复

将占位页接入真正的产物和失败恢复路径。用户看到“页面暂时无法打开”、重试按钮及可理解的提示，不出现要求修改 Rust 源码的说明。恢复网络后由用户重试，避免做题过程中后台自动刷新。

验收：断网冷启动有可操作页面；恢复网络后能重试回到题库；失败页不能因残留权限扩大原生调用范围。

### 5.2 窗口与数据重置体验

可选增加窗口模式与全屏切换、保存窗口尺寸；建议在行为稳定后再做。若增加“重置登录”，明确影响并由用户主动确认，测试使用隔离数据目录，不删除开发者真实会话。

验收：窗口设置跨重启生效；取消重置不会修改任何数据；实际重置范围有文档说明。

### 5.3 三平台发布验证

修正或分别记录 Windows 开发入口；提供 macOS、Windows、Linux 的启动、登录、重启恢复、练习与退出冒烟清单，记录实际 OS、架构、WebView 版本和验证日期。签名、公证与自动更新作为独立后续事项，不混入本轮基础改进。

验收：构建产物和实际运行结果分别可查；未做真机测试的平台如实标注“未验证”。

## 6. 核心验收矩阵

以下全部是后续拟执行项目，本轮没有执行结果。

| 场景 | 必须满足的结果 | 验证层 |
| --- | --- | --- |
| 首次进入目录，按钮延迟渲染 | 包装层最多打开一次登录弹窗，重试有上限 | 模拟 DOM + WebView 冒烟 |
| 历史记录 false，但凭证稍后恢复 | 已确认无需提示后取消所有未执行重试 | 可控时钟测试 |
| 缓存 true，实际 cookie 读取失败 | 不写成 false，不据此弹登录框 | Rust 单元测试 |
| cookie 仍在但网站拒绝会话 | 不声称已验证登录；网站提示仍可操作 | 模拟站点 + 人工验证 |
| 缓存缺失，直接进入练习页 | 包装层不主动弹窗、不重定向 | JS + 路由测试 |
| 练习中失效，之后 SPA 回目录 | 练习期间不打断，回目录按需提示一次 | 联动测试 |
| 提示排队后立即进入练习 | 执行动作前再次检查，取消不合时宜的提示 | 可控时钟测试 |
| 登录后同域和跨域跳转 | 无重载循环，不把练习或报告误送回目录 | 路由测试 + 真机冒烟 |
| 心跳休眠时加载新页面 | 在预定检查窗口内响应，无需等下一轮心跳 | 调度测试 |
| 选择器被站点移除 | 有限重试后停止，页面仍可手动操作 | 模拟 DOM |
| 非授权站点调用原生命令 | 调用被拒绝；授权站点行为正常 | 实际 Tauri 集成验证 |
| 离线启动与恢复 | 可见失败页，用户重试有效 | 真机冒烟 |
| 三平台安装、重启和退出 | 可启动；记录实际登录恢复表现；退出无残留进程 | 各平台人工冒烟 |

“不弹窗、不重定向”指包装层不主动干预；粉笔网站自身的登录提示仍由网站决定。

## 7. 建议拆分的实施批次

| 批次 | 交付 | 依赖与回滚 |
| --- | --- | --- |
| A | 项目约束、说明纠偏、行为样例清单 | 可独立审阅，不改变运行行为 |
| B | 最小测试入口、模拟页面、PR CI | 建立在 A 上；不把失败回归测试直接留在默认 CI，可与对应修复同批交付 |
| C | 登录取消、练习保护、未知状态与调度修复 | 依赖 B；按问题拆小提交，回滚对应实现时保留可用测试基础 |
| D | 远程权限、配置校验与诊断边界 | 先验证真实跳转来源；权限变更独立提交便于定位回归 |
| E | 离线恢复、窗口体验、平台交付改进 | 用户体验项分别审阅；不要求与 C、D 同时上线 |

每个批次交付：改动目的、涉及文件、测试结果、未验证范围、回滚方式。测试与实现一并审阅，不用大段自述替代证据。未经验证的站点行为继续列为假设。

## 8. 审阅时建议确认的范围

推荐先批准 A—C：项目约束、测试与 CI、登录导航稳定性。D 在确认域名和权限后推进，E 中优先离线恢复，窗口偏好与签名更新可以后置。

主要产品取舍是“自动打开登录框”的积极程度：建议保留便利性，但状态不确定时不抢先操作；任何自动提示与跳转都以保护正在进行的练习为优先。

本文是待审阅提案，不代表以上批次已经获准执行。下一步以你的审阅意见确定实施范围。
